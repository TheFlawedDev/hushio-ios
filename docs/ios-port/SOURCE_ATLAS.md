## 1. Runtime map and platform fault lines

```text
src/main.tsx
  appearance/classes, audio hooks, platform services, queue hydration, warm playback
  -> SessionGate -> onboarding/session -> App
     -> Android + phone short side: PhoneShell
     -> otherwise desktop shell (not a generic mobile selector)
        -> CurrentView -> views and shared/phone components
           -> Zustand stores / src/lib actions
              -> src/lib/bridge.ts call/invoke + plugin HTTP
                 -> src-tauri/src/lib.rs generate_handler! and services
                 -> plugin:hushio-player -> PlayerPlugin -> PlayerService (Android only)
```

`src/lib/bridge.ts::Platform` is `windows | macos | linux | android`; `detectPlatform` checks Android, Linux, Mac, Windows. An iPhone UA containing `Mac OS X` can be classified as macOS; other unsupported UAs throw. `src/App.tsx::App` only enters `PhoneShell` when `platform === "android"` and `shellFor(shortSide) === "phone"`. `src/lib/usePhone.ts`, `layoutTier.ts`, `htmlClasses.ts`, `desktopPlatform.ts`, `networkType.ts`, `insets.ts`, `haptics.ts`, `wakeLock.ts`, `main.tsx`, settings row filtering and launch routing each have their own platform decisions. Do not globally substitute “mobile” for “android.”

`src-tauri/src/lib.rs::run` already has some `desktop`/`mobile` separation, but also starts shared services and a loopback proxy unconditionally. `src-tauri/src/mobile.rs` has deliberate tray/window/PiP/update stubs; they are not real iOS adapters. `src-tauri/tauri-plugin-hushio-player/src/lib.rs::plugins` registers Kotlin classes only on Android; elsewhere it registers an empty player plugin. iOS icons are present, but no generated iOS host or Swift implementation was present in the inventory. `Cargo.toml` excludes updater/notify on iOS but this does not prove the remainder builds.

**Tests:** `src/lib/bridge.test.ts`, `desktopPlatform.test.ts`, `usePhone.test.ts`, `layoutTier.test.ts`, `htmlClasses.test.ts`, `networkType.test.ts`, `src/App.test.tsx`, `src/components/phone/PhoneShell.test.tsx`.

## 3. Playback architecture and ownership

### UI to native paths

1. Track row/collection/search actions call `stores/player.ts::playQueue/playTrack/playFromRow/jumpTo`.
2. `startCurrent` sets optimistic playing state, history/listening effects, and calls `load` with a load-generation guard.
3. `lib/audio.ts::playStream` dispatches Android to `androidEngine.ts::androidPlayStream`; otherwise uses two HTML Audio or `NativeAudioDeck` decks.
4. Android: local ID resolves through `bridge.localLibraryTrackPath`; other IDs go through optional add-on resolution then `resolveStream`; `bridge.playerSetQueue([item], 0, startPositionMs)` then `playerPlay` -> Kotlin `PlayerPlugin.playerSetQueue/playerPlay` -> `PlayerService.replaceQueue/setPlaying` -> Media3 ExoPlayer.
5. Desktop/browser: local -> `localPlaybackSource`, network -> `networkTrackUrl`, downloaded -> existence-checked file, otherwise add-on/YouTube/JioSaavn -> register HTTPS URL with Rust -> loopback URL. `NativeAudioDeck.loadSource` -> `desktop_playback_load` -> Rust mpv engine (desktop cfg); HTML deck gets the resolved URL.
6. Android plugin events -> `androidEngine.applySnapshot` -> `mediaEventsFor` -> `audio` EventTarget -> player store/listening. Desktop generation-tagged mpv events -> `NativeAudioDeck.acceptEvent` -> same audio façade.

### What stays shared

`stores/player.ts` is authoritative for user-visible queue semantics, explicit-queue ordering, shuffle/smart shuffle, repeat cycle, autoplay, restored state and history effects. `queue.ts`, `queueInsert.ts`, `smartShuffle.ts`, `autoplay.ts`, `playQueue.ts`, `playSource.ts`, `prefetch.ts` are shared algorithms. Preserve track IDs and metadata (`src/types.ts::Track`), do not replace queue decisions with AVQueuePlayer defaults.

`resolveStream.ts::resolveStream/pickAudio`, `innertube.ts`, `poToken.ts`, `firstSuccess.ts`, `streamingQuality.ts`, `addons/resolve.ts`, `jiosaavn.ts` own catalogue/quality/URL selection. Rust `stream.rs` owns loopback byte serving/range identity and approved local-file serving. Media service owns actual decoding, focus/routes, native snapshots and Android session lifetime.

### Important ownership discrepancy

`K/PlayerService.kt` supports a 500-item native `QueueMirror`, autoplay transitions, append/insert/remove/move, repeat, shuffle, skip-silence, liked metadata and native sleep timer. **The active TS engine only sends a singleton queue for each track.** Repo search found no frontend calls to native append/next/repeat/shuffle/skip-silence/sleep/like commands and no listener for `player-track-changed`. Native media next/previous instead emit actions which `androidEngine` routes to the JS store. Therefore background continuation of the *current* native item is represented, but full queue advancement, recommendation fetching, sleep and stats while JS is suspended are not established. See contracts P3/P6 and discrepancy D02. Native capability tests cannot fill this gap.
